# Native Init base preparation

`prototype.resident-init-prefix/prepare-native-init-base`, `advance-native-init-base!` and `finish-native-init-base!` create a fresh checked native-only Init view in the current persistent World lineage. They retain accumulated source modules, regions, prefixes, executable identities and eval-authority entries. This allows an independent second source leaf to compile without inheriting the first leaf's checked source declarations. A later ordinary graph import can select both issued nodes and freshly check their complete union. No heap merge, Environment splicing or node reattachment occurs.

The operation supports the fixed native Init/meta Init prefix only. It does not generalize native dependencies to Std, Lean or Mathlib, support arbitrary module headers, replace an already published module in the accumulated registry, or grant graph macros permission before completion. Edits still need a retained Context from before the changed module's publication. General Project loading remains a separate integration task.

## Authenticated readiness

The fixed `prototype.globals-consumer-factory/make-source-graph-native-base-factory` uses the existing sixth closed consumer contract. Its options and normal result shape match that contract. The six prior constructors skip the new preprocessing and provenance registration. The changed factory and resident source bytes require a fresh externally accepted consumer digest and loaded-code attestation before genuine use.

Only after successful producer, Source, archive and executable authentication does the opt-in factory record its actual `lean_run_mod_init_core` binding. `native-init-readiness` takes that issued Factory, its exact borrowed Source and the exact returned binding. Copied maps, matching signatures, descriptors or caller-built initializer mappings cannot issue a token. Weak identity buckets use scalar identity hashes, queued weak references and referent identity; lookup never hashes or compares a caller's binding map. Registry values do not retain their own weak binding key, its handler, a World, session or Factory.

Bounded authenticated plan and witness preprocessing derives the complete selected Init module closure and one exact all-phase symbol per module. Before finalization, every query must return actual owned `IO.ok true` through that fixed installed handler. This reuses the native capability's dependency/phase guard semantics. It does not seed guards, execute a native initializer, invoke the guest fallback or admit a new query IR row. A nonempty or unchanged arbitrary guard set is insufficient: a missing split phase or dependency causes false and terminates the operation before finalization.

The low-level token-indexed query returns an owned Bool packet, not import or completion authority. It has no session argument. The staged operation separately verifies the actual current session/configuration binding, Source, profile, prefix and protected code on entry, protected slices and finalizer entry. The query must preserve control, functions, globals, Source and guard identities, except for its owned local IO allocation and release. It executes zero guest instructions; its bounded host query work has a separate ledger.

The fixed metadata ceilings are 4096 plans, 16,384 aggregate import entries, 16,384 actions, 12,288 witness symbols and 1024 selected queries. A module Name has at most 256 spine nodes and 16,384 UTF-16 code units. Plan/witness Name and symbol lengths have a conservative aggregate 64 MiB UTF-8 ceiling. Symbol prechecks bound UTF-16 length; selected symbol UTF-8 encoding then enforces 4096 bytes per symbol and 262,144 bytes total. For `M` authenticated plans and `I` import occurrences, each query reserves `5*M + 3*I` node/edge incidence units; all queries share a 33,554,432-unit ceiling. This is a conservative traversal bound, not elapsed time, allocation or a measurement of every host validation operation. Profile limits separately bound heap scans, CI inventories, native Name attribution and proof helpers.

## Public staging and ownership

Preparation takes a public Context, one captured immutable deferred request, the issued Init prefix, the fixed graph profile, the readiness token and exactly `{:kernel-policy ... :budgets ...}`. The request contains `:text`, `:file-name`, Java `:module-name`, explicit `:roots` and `:initialization :defer`; path IO and inline calls are excluded. Its actual bounded guest header must contain only implicit Init/meta Init. Policy and `{:outer-fuel ... :helper-fuel ... :attempt-fuel ...}` use the existing explicit import ledgers. Preparation parses the header, creates fresh owned request records and retains the native prefix state; it does not start the finalizer or issue a source receipt.

`advance-native-init-base!` takes explicit positive `:max-operations` and `:wall-ms`, optionally an observer. It queries readiness, then invokes the actual existing `SourceModuleImport.finalizeClassic` route. A raw `:handler-completed` event is intermediate: the next outer advance continues the guest frame. Only actual `:done` establishes `:io-completed`. Returned packets are escrowed before validation, accounting or observers. Wall limits apply between operations rather than preempting a host handler.

Successful returned guest events charge outer work or the larger of World-step delta and aggregate helper steps. A thrown backend call may expose only an earlier checkpoint: the operation charges its validated observed delta and retains the remaining reservation, including the full bound when no later guest steps were published. It never invents internal instructions or retries a failed attempt. Failures retain the actual checkpoint/session, owner state and returned packets; subsequent advance/finish calls rethrow the same terminal failure. There is no cancellation, Source close or guessed cleanup operation.

Finish consumes actual finalizer IO and performs fresh strict native checking using the original native projection certificate. It checks the exact CI union, private header, module order, original native Java identities and actual const/extra Name attribution against the new Environment. It preserves existing source registries and executable/admission identities. Existing global cache entries retain their identities; new pure lazy entries may appear. Guard flags and Source identities remain exact. Only after these checks does it release the prior Environment owner in the new branch and adopt the actual returned packet. It returns `:context`, `:request`, `:header`, descriptive `:native-base` and `:progress`, without graph/source receipts. Successful controls compact to a finished tombstone; this is not a retained-byte or RSS guarantee.

## Validation boundary

The [portable record](../measurements/native-init-base.json) keeps the initial infrastructure and fixture failures, bounded diagnostic runs and final checks separate. The corrected accounting Var passed 1 test / 40 assertions across its three cases. The complete optional suite then passed 1008 tests / 93,772 assertions, including all 11 native tests and the existing graph/discovery namespaces. The separately recorded earlier runs preserve their infrastructure, fixture, adapter-status and assertion failures; none is relabeled as passing.

Factory tests use a real tiny Source and actual canonical native handler while explicitly modeling producer build/archive/closure authentication. Staged tests additionally model authenticated factory provenance, initialized guards, compiler output, header/index/witness transport and finalizer envelopes. The fixed readiness handler, public staging, actual Java checking/adoption, G1 assembly, B kernel admission and frontend decoder/installer run through production paths. The independent-leaf case checks A, resets to the native view, publishes independent B, imports `[A,B]` with fresh union receipts, and calls both plus retained old A across all three backends.

Negative cases cover identity/coverage/bounds, weak-key poison/collision cleanup, partial guards, the shared const/extra attribution guard at its first constant, late adoption ownership, actual raw event fault injection and unpublished backend work. Host-only boundary effects are distinguished from actual nested guest helper instructions. These models do not establish a genuine restored frontend/native-base run, arbitrary graph initializers or macros, general projects, resource cleanup guarantees, or a performance improvement.
