# General Lean file loading on the JVM

This research path runs the authenticated original Lean parser, elaborator and compiler on the Java IR runtime. It accepts an explicitly prepared Prelude branch and source capture; it does not recognize source function bodies or replace Lean elaboration.

`general-frontend-file-v1/open-file!` receives the prepared branch, actual source capture, authenticated companion/parser Headers and an explicit branch-retirement callback. It owns its source provider and generated-code scope. Use `load!` to process actual commands through EOF, then `invoke-nat!` for a checked, locally defined, safe monomorphic `Nat → Nat` entry using its exact typed boxed Name. `close!` retires healthy terminal custody. The constructor belongs to the runtime-cohort path: use `prepare-general-source-child!`, which selects the 512-admission driver before its callbacks capture the session.

For each command the original parser runs once. A read-only structural gate validates the actual Syntax before original elaboration. The checked adapter publishes declaration versions. The original compiler supplies canonical IR rows, and generated-batch prepares complete Header/frontier batches before atomic linking. Actual EOF is distinct from `exit`, an unsupported import, a parser/elaboration error and an unsupported execution batch.

The gate currently covers selected standard declarations, namespaces and sections under explicit Prelude. Protected options, unsafe surface declarations, custom commands and unreviewed effects are rejected. This is a bounded compatibility profile, not a claim to accept arbitrary Lean syntax or arbitrary macros safely. Declaration admission currently covers safe individual definitions, theorems and axioms. Equation compiler output can require additional declaration kinds even for a safe source definition; recursive examples expose this outstanding gap. A closed pattern-match example passes after the Float32 transport fix, with substantial first-use helper preparation cost recorded in the corpus manifest.

Host invocation currently has an explicit immutable Nat codec and a 4096-bit input bound. Broader values, bidirectional JVM bindings and ordinary project imports are separate work. Failed files preserve their owner packet for diagnosis; closing metadata is not presented as successful guest unwinding. No failure retry or fake EOF is provided.

Validation is recorded separately in `general-file-validation.json`, `core-native-validation.json` and the two fixture corpus manifests. Selected core syntax files pass hosted checking, compilation and execution. The original proposal corpus remains unchanged and has separate compatibility status. The earlier finite arithmetic acceptance receipt remains historical evidence.
